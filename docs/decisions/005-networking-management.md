# 005: Join Links via Capability Tokens + Cookie Session + Redirect-Clean URL

## Status

Accepted

## Context

HearthVTT must support three deployment modes with a single server implementation:

1. **Hosted (cloud)** — user-friendly, HTTPS/WSS by default
2. **Self-host with tunnel** — user-friendly, secure, pretty links (minimal networking knowledge)
3. **Hardcore self-host (direct IP)** — no DNS, no tunnel, optional LAN-only usage

We want a join/auth flow that:

- is easy for non-technical friends
- avoids secrets living in bookmarks, browser history, Discord previews, or logs
- supports WebSocket auth without query-string tokens
- cleanly separates **Admin** (server owner/operator) from **GM** (in-game authority)
- remains compatible with future hosted mode and multi-server scaling

## Decision

We will use **capability-based join links** that mint a **cookie-based session**, then redirect users to a **clean play URL**.

### Join link format (capability token)

Users join via:

- `GET /join/<inviteToken>`

Where `<inviteToken>` is a long, unguessable token that resolves server-side to:

- `campaignId`
- `seatId` (or a seat claim slot)
- role constraints (player/gm)
- expiry (e.g., 7 days)
- usage limits (typically one-time claim)

### One-time PIN on claim

To mitigate link leakage (e.g., Discord forwarding, accidental exposure), claiming an invite requires a **PIN**:

- PIN is collected once during claim
- only a **hash** (argon2/bcrypt) is stored
- PIN attempts are rate-limited
- after successful claim, the invite token is revoked (or marked claimed)

### Redirect-clean URL

After a successful claim, the server:

- sets secure cookies (see below)
- redirects to a stable URL without secrets, e.g.:
  - `302 Location: /play` (or `/c/<campaignId>`)
    The join token is never meant to be bookmarked.

### Cookie-based sessions (HTTP + WS)

Authentication is handled by a session model:

- **short-lived access token** (in memory or short-lived cookie)
- **long-lived refresh token** stored as `HttpOnly; Secure; SameSite=Lax` cookie
- refresh tokens are **rotated** on use and can be revoked server-side

WebSocket authentication uses the same cookie session:

- client connects to `wss://<origin>/ws`
- server validates session from cookies during WS upgrade
- no auth tokens in query strings

### Deployment routing strategy

We standardize on an origin-based approach driven by `PUBLIC_BASE_URL`:

- **Hosted mode**: `https://hearth-vtt.com/...`
- **Tunnel mode**: `https://<serverId>.hearth-vtt.com/...` (recommended for multi-server routing)
- **Hardcore direct mode**: `http://<ip>:<port>/...` (insecure/LAN/dev option)

Invite links are generated by the server using `PUBLIC_BASE_URL`, so the same codepath supports all modes.

### Admin vs GM responsibilities

- **Admin** manages access and hosting:
  - create/revoke invites
  - rotate links
  - kick sessions
  - set roles (player/gm/spectator)
- **GM** manages in-game authority (actions, encounters, etc.) and is not inherently allowed to manage access.

## Alternatives considered

1. **Single stable URL with edge “steering cookie” routing**
   - Requires custom edge logic (e.g., Workers) and WS proxying complexity.
   - More operational complexity than hostname-based routing.

2. **Embed seat identity or auth tokens permanently in URLs**
   - High risk: tokens leak via bookmarks, history, previews, logs.
   - Harder to rotate/revoke safely.

3. **OAuth / platform accounts required for all players**
   - Increases friction and undermines the “join with a link” self-host UX.
   - Platform accounts remain optional for convenience features.

4. **Self-signed TLS certificates for direct-IP self-host**
   - Causes browser warnings and onboarding pain for non-technical players.
   - Kept as an advanced option; not the default.

## Consequences

- Join links become safe to share temporarily (short-lived, claim-once), and long-term access is via cookies.
- The `/play` URL can be stable and bookmarkable without embedding secrets.
- WebSocket auth is simplified by reusing the cookie session.
- Hosted and tunnel modes share the same UX and URL patterns.
- Multi-server scaling is supported cleanly via subdomains (`<serverId>.hearth-vtt.com`).
- Direct-IP mode remains supported for development and “off-the-grid” users, with clear warnings about lack of HTTPS unless advanced setup is performed.
